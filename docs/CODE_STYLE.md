# WTune 程式風格

## 設計原則

| 原則 | 在 WTune 的做法 |
|---|---|
| 單一職責（SRP） | 一個函式做一件事；超過約 60 行就拆。一個模組一個主題，超過約 1500 行就拆成 package。 |
| 關注點分離 | 計算（純函式）與副作用（檔案、Slurm、子程序、print）分開；計算可以不靠叢集直接測試。 |
| 分層 | CLI（解析參數）→ 流程編排（tune／run／post 各階段）→ 領域邏輯（版面、預測、物理）→ 介面卡（Slurm、WRF 檔案、ADIOS2、外部工具）。下層不 import 上層。 |
| 明確的資料型別 | 跨函式傳遞的結構用 `dataclass`（`frozen=True` 若不需修改）取代字串當 key 的 dict；需要 JSON 時用 `to_dict()`，輸出格式不變。 |
| 依賴注入 | 會碰外部世界的東西（`sbatch_runner`、`sacct_runner`、時鐘）由參數傳入，測試用假物件替換。 |
| 表格式分派 | 多分支選擇用 dict／表格（指令 → handler），不用長串 `if/elif`。 |
| 不重複（DRY） | 同一段邏輯出現第二次就抽成函式。 |
| 型別註記 | 公開函式要有參數與回傳型別；核心模組用 mypy 檢查。 |

## 註解

- **說「為什麼」，不說「做了什麼」**：程式本身說明做了什麼。
- **docstring**：第一行一句話說明用途；必要時再列參數、回傳、副作用，**總長不超過約 6 行**。
- **行尾註解**：用於單位、魔術數字、不明顯的條件，例如 `dt = 72  # s`、`if n < 10:  # WRF 最小 patch`。
- **證據只留一行參照**：`# BP5 讀不回來（wiki: adios2-bp4-restart...、job 2734）`，不在程式裡寫實驗經過；細節放 wiki 或 commit message。
- **不留過期註解**：改程式時一併改註解；說不清楚的註解寧可刪掉。

## 測試

- 重構前先用 golden 測試釘住行為（`tests/test_refactor_golden_*.py`）；重構後同一組 golden 必須通過。
- 測試會 monkeypatch 的名稱若搬家，就同步改測試的替換點，並在 commit message 列出。
